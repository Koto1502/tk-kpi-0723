WITH ev AS (
  SELECT user_pseudo_id u, event_name e, event_timestamp ts, PARSE_DATE('%Y%m%d', event_date) d,
    app_info.version v, geo.country country,

inst AS (

per AS (

    COUNTIF(ev.e = 'session_start' AND ev.ts <= inst.i.ts + 86400000000)                          sessions_24h,

Why ad loads fail: 58% of failed loads are the device being unable to reach AppLovin's server; genuine no-fill is 0.1%.

Every failed load logs ad_request_status with status = fail and the SDK's raw error message. Before requesting an ad, the device looks up the address of AppLovin's mediation server ms.applvn.com (DNS). Two failure messages show that lookup failing:

  • A · Unable to resolve host "ms.applvn.com": No address associated with hostname — the lookup returns nothing. Users are concentrated in markets where AppLovin is unreachable (Sudan, Iran, Yemen, Syria, Cuba, Libya), plus a few individual devices elsewhere with very high counts.
  • B · Failed to connect to ms.applvn.com/0.0.0.0:443 (or [::]:443) — the lookup returns 0.0.0.0, a non-routable address. This is how DNS-based ad blockers (AdGuard, NextDNS, Pi-hole, private DNS) block ad domains. Few users, very high retry counts.

Neither group can be served ads, so the revenue at stake is small. The defect is that the client keeps retrying: the maximum per user is over a thousand failed loads in one week. Group C carries no error message and cannot be classified.
